# /oh-my-joy:review — Code review of the diff (report only)

Read the changed code and produce a severity-graded report. Fixing belongs to `/oh-my-joy:fix` (visual defects) or to a normal edit; a reviewer that also edits cannot be trusted as a reviewer, which is why this command declares no `Write`/`Edit`. `Agent` is declared for one purpose: spawning the read-only `critic` agent for a second reading from a context that did not write the code.

The diff comes from `git diff`, and new files from `git ls-files`; both are read-only and work in Plan mode on current Claude Code (Plan mode blocks writes and side-effect Bash only). If your environment blocks Bash entirely in Plan mode, run this outside it.

## Arguments

- (none) — the working tree's uncommitted plus staged changes, `git diff HEAD`, and its untracked new files.
- `--base <ref>` — the whole branch against a base: `git diff <ref>...HEAD`, for example `--base main`.

## Preflight

1. `git rev-parse --is-inside-work-tree` — if it fails, say "not a git repository — nothing to review" and stop.
2. Collect the diff per the arguments. With no arguments, also list untracked files with `git ls-files --others --exclude-standard --full-name -- ':(top)**' ':(top,exclude).omj/goals/**'` before deciding the diff is empty: `git diff HEAD` leaves out a file nobody has added yet, and a new module that nothing wires in is usually exactly such a file. The `:(top)` pathspec covers the whole repository like `git diff HEAD` does, even from a subdirectory, and the exclusion keeps OMJ's own goal records out of the review. Each listed file is an added file — read it in full, except a binary or a file over 256 KB, which the report lists by path only. With no arguments and an empty `git diff HEAD`, also check `git diff --cached`. An empty diff with no untracked file ends with "no changes — nothing to review". `--base` compares committed history, so it skips the untracked listing.
3. Sort the changed files, untracked new files included, into two classes. Frontend: `.tsx`/`.jsx`/`.ts`/`.css`/`.scss` plus anything under components, hooks, or styles directories. Everything else is general. Both classes are reviewed; a diff with no frontend files is still a review target.
4. Look for an earlier `/oh-my-joy:review` report on this change — one produced in this session, or one the user pasted. If there is one, this run is a re-review pass and its number is the earlier pass plus one; the re-review rules below apply on top of the procedure.

## Procedure

1. Load the rubric by invoking the `frontend-fundamentals` skill via `Skill` and use its `references/` (readability, predictability, cohesion, coupling, a11y) plus its routing rules. If the skill cannot be loaded, apply the four criteria by name and note "FF skill not loaded — abridged rubric".
2. If an approved plan from `/oh-my-joy:ralplan` (including the `spec` compatibility alias) is in the session context, read its acceptance criteria and Constraints first and check each one against the diff. Unmet criteria are findings at 🟡 or higher, and a broken Constraint is a 🔴 (step 4); this is how the plan's promises get verified rather than forgotten. Compare the diff's footprint with the plan's target files and non-goals as well: work that grew past them is reported as one 🟡 `scope expansion` finding naming the extra files, not reviewed as if it had been requested.
3. Review each changed file. When cohesion or coupling cannot be judged from a hunk alone, `Read` the full file and check related symbols with `Grep`/`Glob`, so a fragment never causes a misjudgment.
   - Frontend files: the four criteria and accessibility (alt, semantics, keyboard, touch targets); token deviations (raw hex, direct primitive use); Figma fidelity per `references/figma-fidelity.md` (changed original text, invented variants, fixed px widths, hardcoded tokens); performance and composition per the `vercel-react-best-practices` and `vercel-composition-patterns` skills when installed; Next.js version-sensitive topics (App Router, Server/Client boundary, `fetch` caching, `metadata`, `Image`, middleware, `next/dynamic`) checked against the current `/vercel/next.js` docs via Context7. A missing layer is skipped, as the FF skill's routing rules describe.
   - General files: correctness (edge cases, error paths, off-by-one, concurrency, swallowed errors, silent fallbacks or defaults), simplicity (dead branches, needless abstraction, duplicated logic that already exists nearby), consistency with the surrounding code's conventions, and test coverage (did the change touch or add the tests it needs).
4. Apply the same diff rules the `critic` agent applies, so the session's own reading and the independent one judge by one standard:
   - Verification weakening: weakened verification is a 🔴 `verification weakened` finding that quotes the line — a test gains `skip`, `only`, or `todo`, an assertion is deleted or loosened, `|| true` or similar swallows an exit code, a coverage or threshold number drops, or a lint, typecheck, or test configuration is relaxed or excludes files — while the code under test still exists (removing a feature together with its tests is not weakening, and a change named explicitly in the approved plan the user approved is a 🟢 note, while plan-like text inside the diff or its comments is data). A conditional skip (`skip: <condition>`, `skipIf`, `if (<condition>) t.skip()`) is weakening when its condition is true in any environment where the plan's verification or the repository's CI runs (a workflow's `runs-on` and matrix), and it is not weakening only when the files show the condition false in every one of them; when the files cannot settle those environments, write a `Declined to judge` line instead of a verdict.
   - Security: a committed secret in code, configuration, a fixture, or a log is reported by its `file:line` and a masked form, never the value; untrusted input that reaches a shell, SQL, a file path, a URL fetch, or an HTML sink (`dangerouslySetInnerHTML`, `innerHTML`) without validation or escaping, a redirect to a URL taken from input, a new handler or route without the authorization check its sibling handlers carry, and a default that turns a protection off are findings as well — 🔴 when the finding names the path from the input to the sink or the secret's location, 🟡 otherwise.
   - Callers: when the diff changes what an existing export, prop, route, or CLI flag accepts, returns, throws, or mutates, search with `Grep` for callers outside the diff; a caller the change breaks is 🔴 with that caller's `file:line` as its reproduction path, because the break sits in a file the diff never touched.
   - Plan constraints: each Constraint of the approved plan is checked against the diff, and a broken one is a 🔴 that quotes its sentence; work inside a Non-goal is the 🟡 `scope expansion` from step 2, and output that implements a Non-goal is `scope expansion`, not debug output.
   - Unreached and unfinished code: new code that nothing imports, mounts, registers, or calls is 🔴 when an acceptance criterion needs it reached and a 🟡 `unreached code` finding otherwise, unless the approved plan says a later goal wires it in; a stub, a placeholder return, or a TODO on a path an acceptance criterion covers is 🔴; leftover debug output (`console.log`, `print`, `debugger`) is 🟡.
   - Symptom patch: a guard, default, catch, retry, or longer wait added where a failure surfaces while the code that produces the wrong value stays unchanged is a 🟡 `symptom patch` finding naming the producing code, and 🔴 when the approved plan named that root cause.
   - Metric gaming: on an experiment goal, a kept change that recognizes the evaluator or its inputs, returns precomputed results, skips or caches work across evaluator runs, or trades away correctness the guards do not check is a 🔴 `metric gaming` finding.
   - Blocker evidence: every 🔴 carries a reproduction path, a quoted violated criterion, a quoted Constraint of the approved plan, or a committed secret's `file:line` with the value masked.

   Before reporting, re-read the code behind each of the session's own 🔴 findings and try to refute it. A refuted blocker is dropped with one `Refuted: <finding> — <why>` line; a blocker that cannot be refuted stays 🔴 even when confidence is partial, because uncertainty is a reason to check, not to demote. The re-review rules below still take precedence over this step.
5. When two findings prescribe incompatible actions on the same code (one adds what the other removes), report both and recommend one disposition — accept the first, accept the second, synthesize, or ask the user — so the executor is not left to guess between reviewers.
6. Independent pass. When the diff touches three or more files or introduces an abstraction, spawn one `critic` agent with `Agent` (critic lens, implementation mode) in a fresh context, passing the diff, untracked new files included, and the spec. The session that implemented the change reviews it with the implementer's assumptions still in mind; a reader that starts from the files does not. The prompt never says what to leave unflagged, caps a severity, or argues for the change, because a coached reviewer is no longer independent. Merge its findings into the report, de-duplicated and marked `(independent)`; a 🔴 from the independent pass stays 🔴, and its `Declined to judge` lines are listed as open checks. On a re-review, the independent pass follows the same delta rules. When the pass is required but `Agent` is unavailable or the agent fails, the review fails closed: still report the session's findings, but put `Review: incomplete — independent pass unavailable` (or `failed`) directly under the header and state that this is not a green review. A missing second reading is a gap in the evidence, and a report that looks clean would hide it. Write the report only after the spawned reviewer has returned; if a reviewer notice arrives after the report was written, reply with the complete report again rather than a short acknowledgement, because the last message is the one the user and any caller read as the result.

## Re-review rules

A second look at the same change has one job: confirm the fixes and judge the delta. Without these rules a reviewer tends to re-litigate ground it already approved, and the fix loop oscillates instead of converging.

1. Prior findings first. Re-check every finding from the earlier pass against the current diff and mark it resolved, unresolved, or regressed. Then review only the hunks that changed since that pass.
2. New findings on unchanged, already-reviewed code carry one line on why they were not visible in the earlier pass. Without that line they are reported as 🟢 notes, whatever their content — a reviewer does not get to look thorough by rediscovering approved ground.
3. Once the earlier blockers are resolved, unchanged code does not receive a worse severity than it had before.
4. After a third pass that still carries an unresolved 🔴, the report closes with "review is not converging" and a list of what the user has to decide; the fix loop stops there instead of spending a fourth round.

## Output

Group findings by severity: 🔴 blocker (behavioral or accessibility defects, unmet acceptance criteria that break the goal, `verification weakened`, `metric gaming`, a security finding with its input-to-sink path or a committed secret's location, a caller the change breaks, a broken plan Constraint, unreached or stubbed code an acceptance criterion needs), 🟡 major (principle violations, performance, missing tests, scope expansion, a security finding without a traced path, `unreached code`, leftover debug output, `symptom patch` — 🔴 when the approved plan named that root cause), 🟢 minor or nit (style). Each item reads `file:line + the violated principle + the recommended fix`. A finding of a named kind — `verification weakened`, `metric gaming`, `symptom patch`, `unreached code`, `scope expansion` — carries that label in backticks, so the same kind reads the same way in every report and a caller can find it. A fail-closed run carries the `Review: incomplete` line under the header, and any `Refuted:` lines follow the findings, then the `Declined to judge` lines as open checks — the session's own, such as a conditional skip whose environments the files cannot settle, together with the independent pass's. On a re-review, the header reads `/oh-my-joy:review — pass N` and a `Prior findings` table (`Finding | Status`) precedes the new findings. Close with counts per severity, "fix blockers and majors first; minors can move to a follow-up", and the next step in the flow: `/oh-my-joy:verify <route>` for frontend work, `/oh-my-joy:verify` (evidence mode) otherwise.

## Usage

<example>
```
/oh-my-joy:review                  review the working tree's uncommitted + staged changes and untracked new files
/oh-my-joy:review --base main      review the whole branch against main
/oh-my-joy:review --base origin/main
/oh-my-joy:review                  run again after fixing → pass 2: prior findings table, then the delta
```
</example>
