# Experiment goals

An `experiment` goal measures instead of asserting: the helper runs the approved evaluator, keeps only measured improvements, seals the harness, and restores the scope. This document is the canonical procedure for both stages. `ralplan` reads the Planning section when a request's success is a measured number; `ultragoal` reads the Execution section before it starts an `experiment` goal. The command bodies carry only the trigger, so a run without an experiment goal never loads this text.

## Planning (ralplan)

Experiment goals: when the request's success is a measured number — faster, smaller, a higher score — use an `experiment` goal whether or not a likely fix is known, because only a measurement shows that the change helped. It fixes Metric (name, unit, `lower` or `higher`, and whether the number is deterministic), Evaluator (argv that prints `METRIC <name>=<value>`, fixed inputs and seeds, no network, starting from a clean cache; its timeout and repeats, three or more for a time metric), Scope (the only files trials edit), Sealed (the evaluator, its inputs, and the correctness tests, disjoint from the scope), Guards (commands every kept change passes), and Budget (`maxTrials`, and optionally `patience`, `minImprovement`, and `target`). Set `target` only when the user named a number. The helper rejects settings outside its ranges and the approved settings cannot change afterwards, so keep them inside: at least one guard, and at least one scope and one sealed entry; `repeats` 1–5 and at least 3 unless the metric is deterministic, `timeoutSeconds` 1–3600, `maxTrials` 1–100, scope and sealed entries that are disjoint, relative, outside `.omj/`, not ignored by git, and written with a trailing `/` for a directory. When the repository has no tests, a minimal guard is a syntax check such as `node --check` on each scope file, or a smoke run of the entry point. When no evaluator exists, one change goal before the experiment creates it and its path goes into Sealed. Acceptance states the honest outcome — the best value against the baseline with every trial recorded — and, with a target, "the best value reaches the target (a miss ends as a human-only block)", so the approval screen shows what a miss means.

An experiment plan uses one experiment goal, preceded by one change goal only when the evaluator has to be created. The goal unit lists its kind as `experiment` with its fixed experiment settings. An `experiment` goal also needs at least one commit, because every trial is compared against `HEAD`; in a repository without one, the plan says the user commits first, since ultragoal does not commit.

## Execution (ultragoal)

Init carries the settings the plan fixed: `experiment: {metric:{name,direction,deterministic?},evaluator:{argv,cwd?,timeoutSeconds?,repeats?},guards:[{argv,cwd?,timeoutSeconds?}],scope,sealed,maxTrials,patience?,minImprovement?,target?}`. `status` returns `experimentStatus` with `atBest`, `trialsLeft`, and `pendingTrial`.

Measure through `trial`: `{expectedRevision,goalId,hypothesis,repair?}`. The helper runs the approved evaluator itself, decides keep or discard by the approved rule (the median beats the best measured value by more than the minimum improvement and the baseline's spread, and every guard passes), restores the scope to the best measured state, and returns the decision, the best value, `trialsLeft`, and any `stopReason`; `repair:true` is accepted only after a failing goal review at the best state. The goal's guards still run through `verify` before its review.

An `experiment` goal stays with the lead and is never parallelized, because every trial is measured against the last kept state. After `start`, call `trial` without edits to record the baseline. For each trial, read `status`, choose one hypothesis that differs from every recorded one, edit only scope files, and call `trial` with that one-line hypothesis; the helper keeps or discards and restores. After `invalid` or `restored:false`, undo your own edits by content rather than with `git checkout`, which would also drop uncommitted work the baseline recorded, and make no further edit until `status` shows `atBest`. When `pendingTrial` is set, call `trial` once before editing to recover it (its hypothesis is not measured); an `interrupted` recovery means the host ended the call, so raise its timeout or run it in the background before the next trial. A `helper error: …` recovery means the helper itself failed mid-trial, for example on a scope file it could not restore, and `status` shows the message as `pendingTrial.error`; unlike `interrupted`, it is recorded as a `crash` that spends budget and counts toward patience (a repair trial spends neither), and before a baseline toward `no_baseline`. It is not a timeout, so fix its cause through the resolvable-blocker procedure before the next `trial` call, because the recovery restores the scope and fails again while the cause remains. Give each helper call a Bash timeout above its worst case (repeats times the evaluator timeout, plus the guard timeouts and a margin; the host default is two minutes) and run it in the background only when that exceeds the host maximum (ten minutes in Claude Code), reading its JSON when it completes. Stop when the helper reports a stop reason or no untested hypothesis remains inside the scope, and report which. `no_baseline`, or a `complete` refused for a missed target, is a human-only `block`, because the approved contract allows nothing further.

Reviews on an experiment goal: a 🔴 inside its scope is fixed with a `repair` trial and reviewed again; one in a sealed file, the evaluator, or outside the scope is a human-only `block`, since the approved contract cannot change there. An accepted 🟡 that touches an experiment goal's scope or sealed files, including one from the change goal that created the evaluator, is recorded as a follow-up rather than applied, so the measured best stays the code that ships. The reviewer receives the trial table as factual material. A final-review 🔴 in a completed experiment goal's scope or sealed files is not fixed, because that would change the measured best; report it with the ledger open as human-only, needing a new plan. `close` checks that every experiment goal's scope and sealed files still equal its best measured state.

The Codex adapter follows the same procedure with native terminal calls to the helper; the helper's keep rule, restorations, and recovery are identical on both hosts.
